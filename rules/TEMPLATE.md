# R-0000 ルールの名前

ルールの記録は、失敗とタスクを参照します。失敗やタスクの側からは、ルールを参照しません。

## 目的

このルールで防ぎたい失敗を、目的ごとに1行で書きます。一つのルールが複数の目的を兼ねる場合は、行を分けます。失敗の内容は `failures/` に記録し、ここでは ID を参照します。

| # | 防ぎたい失敗(ID) | 仮定(モデルが何をできない、または知らないか) | 代わりの手段 |
| --- | --- | --- | --- |
| 1 |  |  |  |

## ルールの内容

エージェントに何を求めるかを書きます。実際のルールファイルや hook の実装は置かず、求める振る舞いだけを記述します。

## 判定方法

守られたかどうかを、どう確かめるかを書きます。

- **決定的な検査**: スクリプトで判定できる項目と、その判定条件
- **判断が必要な検査**: 評価者に確認させる観点
- **判定できないこと**: この方法では捕まえられない抜け道

## 置き場所

[`taxonomy.md`](../taxonomy.md) の対応表のどれに当たるかと、その理由を書きます。

## コスト

このルールで増えるものを書きます(常時読み込むトークン、追加のターン、評価者の実行など)。

## 評価タスク

このルールの採否を、どのタスクで測るかを書きます。タスクの定義そのものは複数のルールで共有するので `evaluation/tasks/` に置き、ここでは ID を参照します。

| タスク ID | 用途 | 対象の失敗(ID) | 測る指標 |
| --- | --- | --- | --- |
|  | 調整用 / 判定用 |  |  |

- **選び方**: このルールが防ぐ失敗を誘発するタスクを選びます。タスク側の記録にある、誘発する失敗の ID で対応を取ります。
- **用途**: ルールの調整に使うタスクと、採否の判定に使うタスクを分けます。
- **比較する構成**: ルールあり・なし、または代わりの手段を書きます。構成の比較はルール側の関心事なので、タスク側には書きません。
- 適したタスクがまだない場合は「未定義」と書き、必要なタスクの条件を記します。

## 採否の根拠

- **比較したもの**: ルールあり・なし、または代わりの手段との比較
- **実行条件**: 使ったタスク、モデル、実行回数
- **結果の要約**: 機能、非機能、コストの各指標がどう変わったか
- **判断**: 採用、不採用、廃止のいずれかと、その理由

未測定の場合は「未測定」と書き、採用の理由が推論であることを明記します。

## 再評価の条件

どうなったら見直すか、どうなったら外すかを書きます。
