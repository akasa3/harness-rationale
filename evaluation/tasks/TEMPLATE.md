# T-0000 タスクの名前

## 目的

このタスクで何を測りたいかを書きます。どのルールの、どの目的(防ぎたい失敗)を評価するためのタスクかを示します。

## 課題の内容

- **依頼文**: エージェントに与える依頼の要旨
- **初期状態**: 開始時点のリポジトリの状態(既存のコード、仕様書、テストの有無)
- **規模の目安**: 想定する変更の大きさと所要時間

公開リポジトリなので、ここには課題の考え方と要旨だけを書きます。課題の実データや判定スクリプトは置きません。

## 失敗を誘発する仕掛け

ルールがない場合に失敗が起きやすくなるよう、課題に入れた仕掛けを書きます。

| # | 仕掛け | 誘発したい失敗 | 対応するルール |
| --- | --- | --- | --- |
| 1 |  |  |  |

仕掛けのないタスクでは、ルールの有無にかかわらず同じ結果になり、比較に使えません。

## 判定

### 機能

テストの通過率など、成果物が正しく動くかの判定を書きます。実装者には見せないテストを使う場合は、その旨を書きます。

### 非機能

ルール違反を機械的に数える項目を書きます。

| 項目 | 判定条件 | 種別 |
| --- | --- | --- |
|  |  | 決定的 / 判断 |

### コスト

記録する量を書きます(入力、出力、キャッシュのトークン量、ターン数、所要時間)。

### 判定できないこと

このタスクの判定では捕まえられないものを書きます。

## 実行条件

- **比較する構成**: ルールあり・なし、または代わりの手段
- **実行回数**: 構成ごとに何回実行するか
- **固定するもの**: モデル、ツール、権限の設定など

## 弁別力の確認

このタスクで、構成によって結果が実際に割れたかを記録します。

- 割れた指標と、その差が実行ごとのばらつきを超えていたか
- どの構成でも同じ結果になった場合は、仕掛けを見直すか、タスクを廃止します

モデルが更新されると、以前は割れていたタスクが割れなくなることがあります。その場合も見直しの対象です。
